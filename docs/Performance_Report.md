# SafeBite — Performance Measurements

Generated by `tools/perf-check.mjs`. Measurements are taken over the Chrome DevTools
Protocol with **4× CPU throttling** and **Fast 3G** network emulation (1.6 Mbps down,
150 ms latency) at a 390 × 844 device viewport — deliberately pessimistic, to approximate
a mid-range Android phone on a bad campus connection rather than a desktop.

## Why this is fast enough to demo

- **No framework, no build step.** Total application code is a few tens of KB of plain
  ES modules; there is no bundle to parse and no hydration step.
- **The shell is precached.** On any repeat launch the HTML, CSS, JS and icons come from the
  service worker cache, so the app paints without touching the network — this is the
  difference between the two columns above and the reason a basement seminar room works.
- **Product images are lazy-loaded** and fall back to an inline SVG placeholder, so a slow or
  failing image cannot block or shift the verdict, which is the part the user needs.
- **API responses are cached in IndexedDB** with a seven-day TTL, and a cached product is
  served immediately while the network refresh happens in the background.
- **Rendering is plain DOM from the existing page** — no re-render of the whole tree on
  interaction, and verdict computation is a synchronous pass over a short list of tags.

## Honest limitations

- PBKDF2 key derivation (210 000 iterations) runs on the main thread at sign-in and takes
  a few hundred milliseconds on a throttled phone; the button label changes to
  "Signing in…" so the wait is visible, but moving derivation to a Web Worker would be the
  correct next step.
- These numbers come from emulation, not from a physical mid-range Android device. The
  device test log records real-device behaviour (B-series checks).
